# Library Authoring

A design system library ships two built values — a system and a theme — and consumers compose them with `.extend()`. This page documents the definition-entry contract: what a published library exports, from where, and what must stay out of its published types.

---

## The Definition Entry

Expose your built system and built theme as named exports **`system`** and **`theme`** from one entry module — either the package root or a dedicated subpath such as `/definition`:

```ts
// src/definition.ts (or your package root)
import { createSystem, createTheme } from '@animus-ui/system';
import { color, border, space, typography } from '@animus-ui/system/groups';

export const theme = createTheme()
  .addBreakpoints({ sm: 640, md: 768, lg: 1024 })
  .addColors({ gray: { 100: '#f5f5f5', 900: '#171717' } })
  .build();

export const system = createSystem()
  .addGroup('space', space)
  .addGroup('text', typography)
  .addGroup('surface', { ...color, ...border })
  .build()
  .seal();
```

Alternatively, ship one bundle export carrying both halves:

```ts
import type { LibraryBundle } from '@animus-ui/system';

export const kit = { system, theme } satisfies LibraryBundle;
```

Use `satisfies`, not a `: LibraryBundle` annotation. A broad annotation erases
the concrete system and theme generics before a consumer can infer them.

Consumers extend the named exports directly — each builder takes the value it understands, and a bundle works on both builders (each consumes its half and ignores the rest):

```ts
// consumer ds.ts
import { system as kitSystem, theme as kitTheme } from '@acme/kit/definition';

export const theme = createTheme().extend(kitTheme).build();
export const ds = createSystem().extend(kitSystem).build().seal();
```

Extraction discovers your package through the same imported identifiers the consumer passes to `.extend()` — the discovery tracer preserves `/definition` for host resolution, then derives package ownership separately while walking the package sources.

Rules:

- **Keep the definition entry narrow — and framework-free.** It exports the sealed `system` and `theme` (or one bundle) plus your registered keyframe collections. Components, hooks, utilities, and framework barrels live behind other entry points. The extraction sandbox evaluates the definition graph and nothing else; a framework graph inside it is a hard load failure, not a warning.
- **`theme` is the name.** The loader prefers a `theme` export and accepts the legacy `tokens` spelling during the deprecation window. New libraries use `theme`; exporting two _distinct_ built themes under both names is a load error.
- **Re-export is valid consumption.** A consumer may re-export your `system` and `theme` unchanged instead of extending — the application still builds and extracts against the library definition as-is.
- **Create transforms with `createTransform`.** Cross-system transform equality is the transform's name plus the source text `createTransform` captures at creation — a consumer re-registering your prop with your own exported definition coalesces cleanly, while a same-named transform with a different body fails loud. Bare inline arrow transforms compare by their own source text; prefer named transforms so conflicts carry a useful name.

### Register Keyframes, Then Seal

Keyframe collections are **declared to the system, never discovered**: nothing scans your package entries, and animus never evaluates a module you did not declare into the definition graph. Create collections with the bundle's `createKeyframes`, register them between the two terminals, and seal:

```ts
const bundle = createSystem().addGroup(/* … */).build();

export const { createKeyframes } = bundle;

export const kitMotion = createKeyframes({
  pulse: { '0%, 100%': { opacity: 1 }, '50%': { opacity: 0.6 } },
});

export const ds = bundle.registerKeyframes({ kitMotion }).seal();
```

Two obligations travel together, and both live inside the definition graph:

- **The registration key must equal the export name.** The extractor resolves `kitMotion.pulse` references by the export name at the defining module; the shorthand `registerKeyframes({ kitMotion })` keeps the two identical by construction. Collections stay module-scope named exports — registration is additive to the export, not a replacement for it. A package-root re-export (`export { kitMotion } from './system'`) keeps consumer imports working; the resolver follows the chain back to the defining module.
- **The registering module sits inside the definition graph, which stays framework-free.** Registration is a runtime step the extraction sandbox executes when it evaluates your sealed system; the sandbox runs no DOM, no bundler, and no real React, so a framework graph there fails the load outright.

Consumers who `.extend()` your sealed system inherit your collections through its registration record — no extra steps, with your names visible in their types so a collision is a compile error. The deprecated `from()`/`includes:` verbs perform no registry merge and cannot carry registered vocabulary; consuming a sealed kit through them records a coded `animus.vocabulary.legacy-verb` warning. Registration retains the collections' frame data on the system object your consumers already ship — declared weight, stated here rather than hidden.

## Theme Augmentation Stays Dev-Only

A library augments the compilation-global `Theme` interface **only during its own development**, never in its published types. The final consumer owns `Theme`; a library-published augmentation would intersection-narrow it and silently corrupt the consumer's token types.

The convention (used by the in-repo reference library `@animus-ui/test-ds`): keep the augmentation in a dedicated `dev-types.ts` module that nothing in the entry graph imports, and exclude the emitted `dev-types.d.ts` from the published declaration output.

```ts
// src/dev-types.ts — dev-only, excluded from the published surface
import type { theme } from './definition';

type KitTheme = typeof theme;

declare module '@animus-ui/system' {
  interface Theme extends KitTheme {}
}
```

<Callout
  variant="warn"
  title="Published .d.ts must carry no Theme augmentation"
>
  Verify before publishing: no `.d.ts` reachable from your definition entry may
  contain a `declare module '@animus-ui/system'` block augmenting `Theme`.
  Keeping the augmentation file in the build program is fine (your components
  need it to type-check) — strip its emitted declaration from the package
  output.
</Callout>

## Keep Your Dist Fresh

Under `.extend()` the consumer's extraction sandbox evaluates your **built dist**, while discovery walks your **src** tree when the published package includes it. A stale dist would silently change the merged registries, so discovery reports when a consumed package's dist entry is older than its newest source file. Non-strict development mode warns; strict extraction fails the build. In a workspace, rebuild the library before running a consumer's production build.

---

## Workspace Watching and the Restart Boundary

In a monorepo, dev servers watch the source roots of every workspace package your system declares through `.extend()`. Editing, creating, or deleting a kit source file converges the served extraction live — a file added to a declared kit enters the analyzed universe from its watch signal alone, without being imported first, and a deleted file's CSS leaves with it. Ordinary dependency installs that leave your workspace layout unchanged do **not** require a restart; neither do kit source edits.

Two boundaries are deliberate:

- **Packages installed under `node_modules` are not watched.** A registry-installed library is a built artifact — change it by installing a new version, which the next analysis picks up from disk.
- **Workspace resolution topology changes require a dev-server restart.** Relinking a package to a different directory, relocating or removing a workspace package, switching a dependency between local (linked) and registry resolution, or replacing a watched source root directory itself all change _where_ a specifier resolves — resolution is captured when a session starts, so restart the dev server after any of these. Day-to-day installs and source edits are not topology changes.

If a workspace source root cannot be watched (for example, the OS runs out of file-watch capacity), only that root degrades: the dev server keeps serving, a sticky `ANIMUS_EXTERNAL_WATCH_UNAVAILABLE` diagnostic names the root, and changes under it may require a restart until a later reset re-registers the watcher.
